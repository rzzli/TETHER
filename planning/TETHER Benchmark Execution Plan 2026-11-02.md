# TETHER benchmark execution plan

The owner's active execution goal authorizes the sequence below. It supersedes the earlier reports' recommendation-only status for these stages. Baseline: `114fecf` (2 November 2026). The [benchmark review](<../reports/TETHER benchmarks and methodological advances.md>) supplies the rationale; the [correctness audit](<../reports/TETHER efficiency and comparative value.md>) supplies the three reproduced defects. Earlier results, failed model attempts, releases and scientific limitations remain historical records.

## Execution and completion rules

Complete and validate each numbered stage before executing the next. Independent work within a stage may proceed in parallel. Retain unsuccessful attempts, fix minor failures autonomously, and commit after major validated changes. A checkpoint records completed work, current work and the next stage. An unfinished or blocked stage remains unchecked. The overall goal remains active until all five stages have current evidence.

No paid provider access or new human review is required. Small public benchmark/dependency acquisition needed for these authorized stages may proceed in isolated project paths, with versions, licenses, hashes and sizes retained. Use local computation and explicit budgets. Account-gated files or authorization that cannot be obtained from the current public route are owner issues; do not invent access, credentials or outcomes. The old downloader and stopped monitor remain untouched. New benchmark protocols do not retry closed historical model cells.

## 1. Correct the three defects (BG01)

- CE01: prevent verification reports from overwriting input receipts, queues or sources, including path aliases. Publish to a fresh destination and preserve evidence on collision/failure.
- CE02: retain validated adapter-reported usage when it exceeds the reservation, account it even on failure, record the breach and stop later dispatch. Reconcile archived responses against recorded usage; malformed or unavailable usage remains unknown/estimated.
- CE03: check receipt-derived availability for every supplied raw policy node, including unused granted nodes. Reuse the eligibility relationship and retain valid alternative availability bases.

Add failing regressions before corrections. Qualify TETHER 0.5.1 with engine 0.3.12; preserve the previous wheels and sealed outputs. Run affected suites, full applicable validation and installed smoke/negative checks. New semantics must not be silently attributed to older runs. Mark complete only when every defect has a red-to-green witness and applicable regressions pass.

## 2. Compare an independent equal-policy validator (BG02)

Write a versioned policy specification and coverage map from the actual supported TETHER contract before comparison. The comparator must enforce the same declared obligations over the same inputs; it must not call TETHER's admission/verification implementation. Any unsupported obligation is a blocker to an equal-policy claim, not an exclusion made after results.

Define expected decisions separately from both implementations. Include eligible inputs, valid near misses, temporal and publication violations, hypothesis mismatch, unavailable/evaluator-only ancestry, missing/cyclic lineage, receipt contradictions, malformed evidence and relevant accounting/recovery records. Existing public counterexamples are development regressions. Separate additional frozen constructions from them and document exposure; artificial cases do not establish natural fault prevalence.

Run paired identical-input comparisons against TETHER, the independent validator, a hash/schema diagnostic ablation and a reject-all sanity control. Preserve all scheduled terminal dispositions. Report false admission and false rejection separately, with replay/accounting/recovery agreement, wall/CPU time, memory where measurable, logical bytes and implementation/maintenance surface. Recompute results independently. Equal correctness with higher TETHER cost is a valid negative result. Do not create an advantage by weakening the comparator.

## 3. Add and evaluate SciFact (BG03)

Pin the public data release, native task/evaluation specification, licenses, exposed examples and source hashes. Keep reference labels/rationales evaluator-only. Define tuning, calibration and evaluation groups before candidate scoring; public development evaluation is not a private leaderboard test. Preserve source/claim grouping and all failure denominators.

Implement native data/evaluation adapters and a task-capable evidence-selection/entailment route. Exact byte matching or replaying supplied gold answers is insufficient to complete this stage. A local model or trained baseline may yield weak results; report them honestly. Retain the official claim/evidence scores alongside TETHER admission and source-replay outcomes. Compare the same candidate-producing configuration with and without the relevant checks, including useful correct-and-admitted outputs, false rejection, abstention, failure and cost. Validate against the native scorer and independent small controls; never claim biological truth from provenance alone.

## 4. Add one LAB-Bench task family (BG04)

Choose LitQA2 or DbQA using source feasibility and the intended use, before inspecting candidate performance. Pin the public release and native task definition. Qualify source access and licenses; isolate reference answers and privileged passages. Full original-task scores and any explicitly limited derivative evaluation must remain distinct.

Implement the selected task adapter, source retrieval and answer-producing route with native multiple-choice scoring. Run a predeclared representative evaluation with all scheduled cases retained. A mere parser, one handpicked answer or reject-all run does not fulfill this stage. Report scope, answer accuracy, correct-and-admitted utility, false rejection, abstention, source support and cost; compare identical base producer/source/tool affordances under the relevant harness conditions. Explain unresolved source access or contamination rather than filling gaps from reference answers. A small engineering pilot does not establish statistical power.

## 5. Test an Inspect-based implementation (BG05)

Pin an isolated Inspect installation. Implement a real runner/scorer extension for the specified obligations, using the independent policy implementation where appropriate and recording this dependency. Run the same frozen conformance cases and candidate artifacts through it, with identical policies. A conceptual comparison or thin launcher alone is insufficient.

Compare correctness, retained failures/accounting/replay, execution cost, integration code and maintenance surface against the standalone route. Distinguish Inspect's native guarantees from extension code. Report missing parity honestly; do not silently omit obligations to obtain simplicity. Add benchmark adapter integration only where needed to substantiate the tested interoperability claim.

## Evidence and final audit

Each stage retains its protocol/code/data pins, commands, failed and successful logs, result tables and a scoped validation record under a fresh directory. Bulk benchmark data, model weights, evaluator answers and generated runs remain ignored; sanitized provenance and compact reports are tracked. Documentation must separate an implementation, an executed evaluation and a scientific conclusion.

The final audit traces every requirement above to actual files and execution results. It checks source/version equality, policy parity, native scorer agreement, denominator completeness, test results, data rights/exposure, existing artifact preservation and unresolved blockers. It does not replace current evidence with old test counts or mark proposals as complete. A final report identifies both useful improvements and negative results. Owner declarations/publication and unrelated clinical/MR/T2–T5/H6 programmes remain outside this goal.
