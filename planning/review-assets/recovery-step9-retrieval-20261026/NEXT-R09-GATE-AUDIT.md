## Minimum finite continuation

Prospectively choose **one** of the already versioned retrieval policies and one invented source-authorized development case. Choice is an engineering scope declaration, not a scientific superiority claim. Freeze exact allowed/visible source identities, AsOf1/adaptedVB5 role adaptation, baseline query/method/pointer policy, source-ID history representation and one default aggregate case budget. No second-policy cross-product is required by Step9.6; configurability already exists and need not be an exhaustive experiment.

Deterministic outputs must retain empty generated interpretation, exact source bytes and truthful missingness. The recorded content is invented transport stimulus, not human gold or model performance. Parent authority, accounting, neutral views and failure denominators should compose the existing runtime components, not introduce a scheduler or reinterpretation service. Keep both track labels and their provenance distinct.

This is one new four-arm execution fixture, not two duplicate runs funded by silently resetting the case budget. The other track can retain its separately bound preparation and existing fixed-evidence regressions; do not claim both tracks newly executed. If a later protocol executes both on one case, their aggregate allocation must be explicit before execution.

**Run a finite preflight before capacity changes.** First calculate the actual full-frame byte reservations and context/output limits for this exact composition, including final source-ID history framing. If it does not fit the unchanged case budget, retain the failed preflight and stop that finite attempt. Do not silently shorten sources, reduce the adaptation, try multiple policies until one fits, inflate budget, or count deterministic baseline work as model calls.

If the chosen source-complete design already has a concrete byte-proxy failure and trusted token quotes show it fits the unchanged token budget, a narrow explicitly versioned token-capacity integration is justified. The rich exposed0.3.4 example established that this situation can occur; it does not prove every new retrieved composition fits. Capacity work is conditional on the declared payload design, not an automatic prerequisite for two-track preparation or a reason to build a generic model-routing framework.

## Capacity is a real interface boundary, not a quotation shortcut

Current `StudySession._capacity` enforces input_quote >= prompt_UTF8_bytes+32. Merely setting `BackendCapabilities.tokenizer_identity`, returning a smaller quoted token count, or wrapping the backend cannot satisfy it. Actual token-aware execution would need a deliberate new session/verifier capacity contract with explicit trusted policy, exact prompt/spec/model/quote receipt bindings and aggregate reservations. Default byte policy and verification of old receipts must retain their existing meaning. No backend-ID branch, monkeypatch, forged usage or silent relaxed quote check is acceptable.

The tokenizer helper is already available; do not duplicate its process/asset/parser implementation. Its old0.3.4 receipt also binds the old complete executing package. A later package cannot call that receipt current merely because model bytes and token counts are familiar. Preserve the old receipt and use a separately authorized compatible verification route or, more simply for the new current route, newly qualified current-package quotes. This assessment authorizes neither tokenizer execution nor any model generation. Exact hypothetical histories remain exact measurements, not universal BPE maxima; any future different payload needs its own bound.

## Actual gates versus legitimate preparation

No missing acquisition, reviewer name or scientific answer key prevents the invented authority-aware four-arm integration and finite payload preflight. Those are still-required engineering tasks with concrete inputs already present. Scientific track, question/baseline suitability, representative case/source sufficiency and the final confirmatory comparator must be frozen for the real study; the present choices can be explicitly development-only rather than pretending they are scientifically finalized.

Native reopening remains subject to a separately reviewed versioned experiment and R07's retained stop. Full H5 protocol selection occurs later in R11 after the human development pilot, so it cannot reasonably be required before all R09 testable mechanics exist. Conversely, completing invented integration cannot waive those later gates or turn common access manifests into four actual scientific systems.

Recommended next disposition: after0.3.5 acceptance, authorize only the single-policy authority-aware four-arm contract and exact bounded preflight first. Continue to the recorded integration if it fits; if it fails, retain that result and decide the narrow capacity extension on the concrete evidence. There is no justified blanket human stop, and no justification for an unbounded strategy/model/controller expansion.
