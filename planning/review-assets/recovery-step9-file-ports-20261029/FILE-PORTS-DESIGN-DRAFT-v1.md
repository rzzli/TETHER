# Minimal Win32 file ports and exclusive sink — design draft

This is a file-only proposal before implementation. It preserves the original 300-second origin, work cutoff at295 and hard cutoff at300; the accepted bootstrap/handoff source remains unchanged. Production-engine continuation, real entry activation and live file qualification are pending. The original launch SDK remains disabled. No target DLL/model/tokenizer, process, Job, registry, network-client or compiler port is added.

## Typed boundary and ownership

The proposed direct file-export census is14 functions: `CreateFileW`, `GetFileType`, `GetFileInformationByHandleEx`, `GetFinalPathNameByHandleW`, `GetFileSizeEx`, `ReadFile`, `CloseHandle`, `GetFileAttributesExW`, `FindFirstFileExW`, `FindNextFileW`, `FindClose`, `CreateDirectoryW`, `WriteFile`, `FlushFileBuffers`. The narrow addition `GetFileType` makes the disk-file requirement explicit; attributes alone are not a claim that an arbitrary handle is a regular disk file. Its unknown-type return is distinguished from failure by the documented error result. [Microsoft GetFileType](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfiletype).

`CreateFileW` and `FindFirstFileExW` document `INVALID_HANDLE_VALUE` as failure. Their unexpected null/zero result remains unknown and grants no guessed ownership or close; this prospectively corrects the earlier broad proposal. A Python-visible valid handle enters its preallocated owner slot before identity, clocks, formatting or logging. Search slots have `FindClose`; original/output file slots have `CloseHandle`. Once-only close intent is retained before dispatch, and failed/unreturned closes are never retried. This is application ordering after FFI return conversion, not an atomic OS-to-Python guarantee. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [FindFirstFileExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw), [FindClose](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findclose).

Existing pure interfaces expose a reservation acknowledgment, but the concrete sink must track namespace ownership separately from reservation readiness. If directory creation returns true and journal/reservation setup then fails, the owner retains that directory capability and every partial output slot for cleanup. No original reads begin until reservation-file close and the first journal record/flush have known acknowledgments. A failed/unknown directory creation grants no writes into that namespace and is not retried.

## Original files and metadata

Original opens are read-only, share-read only, OPEN_EXISTING, OPEN_REPARSE_POINT|NORMAL, noninheritable. Same-handle identity checks require disk type, no directory/reparse attributes, a bounded final DOS path matching the admitted original spelling under the frozen lexical rule, and exact declared signed64 nonnegative size. A returned final path that is too long or missing termination fails rather than causing a size-probe retry. The future source-bound roster will have explicit roles; there is no general large-file exception or reported-platform-image open.

One reusable65,536-byte read buffer is used synchronously. The returned flag/count and known-byte increment are recorded before slicing, hashing or post-call deadline checks. A false/unknown result does not define a received count, even when its raw count cell looks plausible. Late known bytes remain known but are not hashed after work expiry. Per original read-attempt cap is `ceil(B/65536)+16`; zero progress is an immediate incomplete result. There is one original pass, with live leases retained through all work gates. [ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile).

The directory attribute index and two run-root scans use only predeclared paths. No `Path`, `os`, glob, stat, lstat, resolve or high-level fallback supplies a platform check. Each scan retains return order and bounded raw592-byte Windows SDK `WIN32_FIND_DATAW` records, then sorts a separate lexical comparison index. The installed10.0.26100 Windows declaration excludes obsolete fields still shown in Microsoft's broad synopsis. First/next-result failures leave output buffers undefined; only an established iterator ending with ERROR_NO_MORE_FILES is natural end. A source-declared empty directory may use the explicit contemporaneous-directory-attributes + INVALID_HANDLE_VALUE/ERROR_FILE_NOT_FOUND branch; other initial failures remain incomplete. [FindNextFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findnextfilew).

## Finite admission, not an assumed fit

The full future exact roster is not supplied by this draft. Let N be all unique original files including B early bootstrap originals, M captured own modules, U unique admitted directory nodes including the future output leaf, and S directory iterators across the two scans. B/M≤16, U≤1024, S≤16, and N≤256 are ceilings only. Every future exact source/archive/owner/bootstrap/payload leaf counts once; early leaves are adopted without reopening or rehashing. A mini-plan admits only the externally pinned bootstrap leaves. The full pure plan must then fit before any remaining original is opened.

Proposed durable event bound is `6N+2B+2M+4S+2K+F+128`, with K=13 fixed owner-stage pairs and F=7 fixed bootstrap/finalization events. The extra2B preserves early-source identity reservation/return frames; search events are bounded per iterator, not per entry or API/read. The exact future plan must satisfy this bound≤2048, all row/byte reservations, report/capture memory and API-call bounds. It cannot inherit the old `6N+64+128` assumption or silently omit leaves. These formulas still require machine-contract review.

## Output and acyclic sealing

The sink uses one new directory and a closed nine-basename set. Each output uses CREATE_NEW, no sharing, GENERIC_WRITE|FILE_READ_ATTRIBUTES and noninheritable synchronous flags, then same-handle disk/attribute/final-path/zero-size checks before any content write. Successful short writes advance known counts before post-call checks and continue only within the frozen finite cap. Failed/unreturned writes are not retried; there is no seek, rename, delete or overwrite route. [WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile).

The DAG is reservation → journal/work → nonfinal candidate → original-lease cleanup → journal close → receipt → terminal seal → final original-clock acknowledgment. Candidate closure is recorded by the cleanup/receipt; journal and cleanup closures by the receipt; receipt closure by the seal; the seal's own close and final clock only by the owner-local returned acknowledgment. The journal's final plan-reservation record precedes its flush/close; there is no append after the bound tip and no self-hash. Optional primary/late/after-seal failure markers are authoritative vetoes. Missing/unknown output return or final-clock failure stays incomplete even when a complete-looking seal exists. No post-hard-deadline I/O is started to force a marker.

The unchanged proposed output bounds are9files, journal8MiB/2048records, four reports≤2MiB each, reservation/three vetoes≤8192 each, total16,809,984bytes. Formula `Rj+ceil(Bj/65536)+16` bounds per-file WriteFile attempts (journal record cap2048, others1), maximum2460. Flushes are journal record acknowledgments plus one final per opened file, at most2057; CloseHandle file attempts≤N+9, FindClose≤S. Performance/300-second fit remains unmeasured. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

The forthcoming machine contract will state exact layouts, flags, error/definedness records, slot state transitions, API/event/source formulas and the bounded fake-fault plan. This document does not construct ctypes, file ports, sink, runtime authority or a new full profile pack, and grants no original-file, payload or SDK operation.
