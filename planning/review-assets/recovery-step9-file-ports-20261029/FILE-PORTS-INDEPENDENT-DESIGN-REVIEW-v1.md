# File-port design review

The frozen v1 design needs one correction before implementation: its file-leaf grammar cannot represent the drive-root directory nodes required by its ancestor index. The referenced `source_key` rejects both the three-character `C:\` spelling and an empty post-drive component. Add a distinct metadata-directory rule for approved drive roots derived from the finite roster, count them in `U`, and keep original/output leaf rules unchanged. Failed or unknown root attributes still block ancestry completion. The author confirmed this gap; v1 remains unchanged.

No other material design contradiction was found in this finite review. `CreateFileW` and `FindFirstFileExW` document `INVALID_HANDLE_VALUE` failure; treating unexpected null returns as unknown is appropriately conservative. Search handles require their distinct closer. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [FindFirstFileExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw), [FindClose](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findclose).

The proposed raw-result, count and ownership ordering preserves known returns before later exceptions. Failed search buffers remain undefined, and iterator order cannot be assumed sorted. [ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile), [WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile), [FindNextFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findnextfilew).

The event/call/output arithmetic is internally consistent as a prospective upper bound. At the declared symbol ceilings the event formula gives 1,825 events, while actual roster admission, elapsed cost and memory fit remain unestablished. The author confirmed that output API observations stay in the owner registry rather than adding recursive journal events, and that a late known write retains its immutable prepared bytes while hashing may remain pending. A partial or late operation must not produce a successful pin.

The final seal cannot witness its own close or the final clock; the separate owner acknowledgment remains necessary. Flush and close outcomes are explicit parts of that future proof. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle).

This review used design/source text and official documentation only. It did not construct ctypes bindings, call a file API, scan a directory, authenticate source closure, replay an old run or access model/CPU/pack bytes. Source/pure implementation and eventual harmless platform qualification still require separate review and authority. Every profile qualification flag remains false.
