## Source configuration and CRT decision

For the selected MSVC x64 branch, local `pyconfig.h` describes `win_amd64`, 8-byte pointers and `Py_ssize_t`, 2-byte WCHAR and shared Python DLL imports. `_DEBUG` selects `Py_DEBUG` and `python311_d.lib`; `Py_LIMITED_API` selects `python3.lib`; the ordinary release full API selects `python311.lib`. These are source-level branch interpretations, not a captured macro dump or `sizeof` result.

The retained C79 component used `/MT` in a standalone fake-target EXE. The new extension needs its own coherent release x64 build recipe. Prefer an explicit `/MD` decision for all extension/C3 translation units, `_DEBUG`/`Py_DEBUG` absent, and exact selected Python include/import-library paths. Every allocator/free ownership pair and any cross-module object boundary still needs source review. Microsoft distinguishes the [DLL CRT `/MD` and static CRT `/MT`](https://learn.microsoft.com/en-us/cpp/build/reference/md-mt-ld-use-run-time-library?view=msvc-170) and requires matching runtime options across linked objects. The old `/MT` carrier COFF must not be silently linked into a differently configured extension.

The local Python images' linker version 14.44 and selected installed toolset 14.51 are recorded separately. This audit neither requires exact compiler-version identity solely from those metadata words nor claims compatibility solely because both are x64. A reviewed compiled extension test is still needed. Python's [Windows extension documentation](https://docs.python.org/3.11/extending/windows.html) explains the import-library role; Microsoft's [PE/COFF specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) supports the metadata interpretation used here.
