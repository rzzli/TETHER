## Training exposure and comparison scope

[The author's training documentation](https://github.com/dwadden/multivers/blob/a6ce033f0e17ae38c1f102eae1ee4ca213fbbe2e/doc/training.md) explicitly identifies fever_sci as the output of stage 1: FEVER, PubMedQA and Evidence Inference, before target-dataset fine-tuning. This supports a zero-shot SciFact arm with the actual released architecture. The scifact checkpoint adds target supervision with 20 sampled negatives per positive. A 10-negative training variant is documented, but the downloader does not expose a distinct scifact_10 checkpoint.

[The paper](https://aclanthology.org/2022.findings-naacl.6.pdf), Tables 1/7 and sections 5.2/B.2/B.3, reports 1,109 SciFact training claims, private-test evaluation, SciFact-driven hyperparameter choices, 440M parameters, and S2ORC encoder pretraining. Since our original public train has 809 claims and dev has 300, public-dev inclusion in the released target checkpoint is strongly indicated; **exact checkpoint training IDs were not verified**. Do not call that checkpoint a clean public-dev baseline. Fever_sci avoids documented target fine-tuning, but inherited model-selection exposure and possible scientific-corpus overlap remain. It is not certified globally contamination-free.

Prospective comparison: preserve the baseline's retrieved top-five documents to isolate solver changes; run fever_sci zero-shot, then optionally fine-tune on the existing 380-claim fit partition and choose settings using only the 82-claim tune partition. Preserve the 69 calibration claims and all 300 dev claims from new fitting/tuning. Existing 427 annotated fit pairs supply supervision; adding arbitrary unannotated retrieval negatives would change the baseline's annotation-relative contract. Extra pretraining differs from the sparse baseline's training budget and must be disclosed. The public dev set has already informed this research program, so it remains a development comparison, not a fresh blind test.

## Context and cost limits

This model jointly uses the claim, title and **one complete abstract**, not multiple full papers. The [Longformer config](https://huggingface.co/allenai/longformer-large-4096/blob/b190dd42e462d2dee634d1162c839710079f97ab/config.json) specifies 24 layers, hidden size 1024, 16 heads, attention windows 512 and 4098 position embeddings (4096 usable sequence tokens). The released Longformer tensorizer does not truncate automatically. Count exact input tokens before dispatch; any overflow needs a declared separate policy, never silent truncation or dropped sentences.

The 440M-parameter FP32 weight floor is about 1.76 GB, excluding activations, temporary tensors and runtime overhead. A 16 GB GPU is a plausible batch-one inference target. Training documentation reports single-GPU training on 11 GB cards with gradient checkpointing; this supports feasibility, not a local guarantee. Baseline-matched dev inference is 1,500 claim/abstract pairs at k=5; k=10 doubles work and changes retrieval. Twenty epochs over 427 fit pairs would require 8,540 forward/backward microbatches and up to 1,080 optimizer steps with effective batch 8, before tuning. This is a prospective workload calculation, not measured time.

No CPU/GPU throughput has been measured. After qualification, a bounded fit-only/fictional smoke set should measure load time, warm throughput, peak RAM/VRAM and token-length scaling, then estimate full work from those measurements. CPU execution is technically available through Longformer's PyTorch attention implementation but is not yet a practical time-qualified fallback. The remaining execution gates are environment/adapter parity, checkpoint deserialization and integrity, length audit, and measured resource capacity; public checkpoint availability is not the blocker.
