# Bounded Job notification diagnostic: source-only design v1

This is a specification for one separately frozen and separately authorized **overflow-only diagnostic**. It does not authorize an attempt, qualify a launcher, accept TotalProcesses=2, explain the prior failures, or enable ABI execution. The compiled-worker qualification failed; resources passed and overflow failed, with sleep and suspended_abort unattempted. That result remains negative. The independent result verifier supplies its exact evidence pin before a prospective diagnostic protocol can freeze.

Use the unchanged own EXE `0100ee6004531a41a28156385ad66fd5c0bded43c4840091a846573efe6d8e49`, source `11490803ed4a3e68937c7bf685f31a042752f3c8681347c67f2bf4cd46721be6`, and frozen SDK `c111ac5f42209eb61fc49522d4cd6db544987b1c4230577404022e1add6eb2f4`. Preserve the exact five-argument worker route, protocol copy/hash, executable identity, environment, working directory, restricted three stdio handles, JOB_LIST creation, suspended checks, sole resume, capture, lease and terminal-seal machinery. No worker/build changes, upstream DLL inputs, notification-limit configuration, observer child or observer thread are needed. Original SDK execution stays disabled.

## Evidence question and bounds

Collect the first observed counter discrepancy, the names and values of any Job messages actually dequeued, and metadata obtainable for their reported PIDs. Separate observations made before a stop request, immediately after TerminateJobObject returns, after owned-child exit, and after releasing observer handles. These intervals can locate the first **observed** difference relative to calls. They cannot establish the kernel event time or sole cause.

Retain the existing 60-second parent, 8-second case, two seconds reserved for cleanup, 256 MiB process/Job commit, active-process limit 1, 64 KiB per captured stream, 40 raw snapshots and 16-PID snapshot buffer. Reserve four of the 40 snapshots for the stop boundaries; the pre-stop portion cannot exceed 36. New global observation bounds are 64 dequeued packets, 16 distinct PID metadata records, 1,024 GetQueuedCompletionStatus calls and batches of at most eight packets. All queue calls use timeout 0. No INFINITE waits. A reached bound is retained as an incomplete observation and initiates cleanup; cleanup cannot be skipped because an observation budget is exhausted. Deadlines bound scheduling; they cannot preempt a synchronous Windows API stalled inside the kernel.

## Minimal API delta and setup

Add only these bindings to the existing typed kernel32 facade:

| API | Arguments | Result |
|---|---|---|
| CreateIoCompletionPort | HANDLE, HANDLE, ULONG_PTR, DWORD | HANDLE |
| GetQueuedCompletionStatus | HANDLE, pointer(DWORD), pointer(ULONG_PTR), pointer(PVOID), DWORD | BOOL |
| OpenProcess | DWORD, BOOL, DWORD | HANDLE |

On the pinned x64 interpreter, ULONG_PTR is eight bytes. `JOBOBJECT_ASSOCIATE_COMPLETION_PORT` contains PVOID CompletionKey then HANDLE CompletionPort: size 16, offsets 0 and 8. The lpOverlapped output holds a message value; **never dereference it as an OVERLAPPED pointer**. Assert these layouts in pure tests and against the pinned SDK header. Existing identity, wait, CloseHandle, SetInformationJobObject and query bindings are reused. [Microsoft CreateIoCompletionPort](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-createiocompletionport), [GetQueuedCompletionStatus](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getqueuedcompletionstatus).

After unchanged Job limit configuration, while the Job is empty and before stdio/child creation, call CreateIoCompletionPort(INVALID_HANDLE_VALUE, NULL, 0, 1). Register its returned handle immediately, independently of subsequent failures; ensure it is noninheritable. Associate it with this exact Job using existing SetInformationJobObject class 7, the 16-byte struct and a fixed nonzero protocol key, then retain the empty raw snapshot. Failure aborts before any child creation. Preserve JOB_LIST and the existing HANDLE_LIST containing exactly the three stdio handles; neither the completion port nor PID query handles may be inherited. [Class 7 documentation](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-setinformationjobobject), [association structure](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port).

## Queue and PID evidence

For every queue call, durably append the contract's call row before interpreting it: sequence, phase, monotonic start/end, timeout 0, BOOL result, immediate error on failure, raw output values, and whether the outputs are defined. FALSE/NULL with WAIT_TIMEOUT (258) ends the current drain only; byte count/key are undefined in that case. A successful NULL lpOverlapped is a valid non-PID Job packet. FALSE/non-NULL can contain a failed-I/O packet; preserve it and stop, without interpreting it as an authenticated Job PID. Other errors, wrong completion keys and unclassified messages retain an uncertainty/failure and trigger cleanup. Each drain yields after eight packets so capture and deadlines still run. [Queue return semantics](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getqueuedcompletionstatus).

Use pinned winnt.h message values. PID-bearing documented IDs are 2, 6, 7, 8, 9, 10 and 11. Message 3 ACTIVE_PROCESS_LIMIT and message 4 ACTIVE_PROCESS_ZERO carry NULL, so no PID may be invented for them. Accept a PID for query only from a successful packet with the exact completion key, a documented PID-bearing ID and a positive value representable as DWORD. Unknown/null/out-of-range payloads are retained without a process open. Limit the metadata table to 16 distinct values; a seventeenth remains visible in the bounded raw packet but is not opened. [Job message definitions and caveats](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port).

Open each permitted PID at most once using OpenProcess(0x00101000, FALSE, pid): PROCESS_QUERY_LIMITED_INFORMATION plus SYNCHRONIZE. Register a successful handle immediately. No privilege change, access fallback, PID reopen, process enumeration, PPID query, module enumeration, image-file open/hash, memory read or process mutation is allowed. Keep observer handles in a separate registry which has only query and close operations; never pass them to terminate/resume/wait-with-nonzero-timeout methods. Owned-child cleanup still acts exclusively on the Job/directly created handles. [OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess), [process rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights).

For each successful query handle record separate outcomes/errors and start/end times for GetProcessId (must equal the packet PID), QueryFullProcessImageNameW(flags 0, fixed 32768 WCHAR buffer), IsProcessInJob(handle, exact Job), WaitForSingleObject(handle, 0), then GetProcessTimes (four raw FILETIME values), in that order. Reject zero/truncated image lengths as unavailable; never reopen the reported path. Only a successful signaled wait preceding GetProcessTimes makes exit time meaningful; otherwise retain raw exit FILETIME as explicitly undefined, even if the process exits during later queries. Access denial, process gone, failed metadata query or nonmembership is evidence of uncertainty, not proof a Job event did not occur. [Image query](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew), [times](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes), [membership](https://learn.microsoft.com/en-us/windows/win32/api/jobapi/nf-jobapi-isprocessinjob), [zero-time wait](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

## Required ordering and handle effects

1. Retain empty, assigned-before-resume and first-running snapshots through the existing SDK path. Associate before creation, drain after creation and before resume, and poll the queue between existing capture/wait polls after resume. Existing periodic sampling remains bounded; a nonempty drain may request one additional raw snapshot per batch within the same 40-sample budget.
2. Keep the generic SDK total1 predicate unchanged. Every raw observation and its failed predicate must be durable. A running counter anomaly stops work immediately and is the stop reason; the diagnostic is allowed only to collect bounded cleanup evidence afterwards. A cap trigger remains the exact existing overflow exception, with retained/observed byte counts. It is never renamed into a successful qualification.
3. On cap, counter anomaly or another failure, retain `before_terminate` raw snapshot immediately before the durable termination reservation. Then call TerminateJobObject on the owned Job. Record its return/error, followed immediately by `after_terminate_return_before_wait` raw snapshot. No queue drain or PID query goes between the pre-call snapshot/reservation and termination, or between return recording and its raw post-call snapshot. Observation/publication failures cannot prevent the cleanup termination attempt; missing boundaries make the interval incomplete.
4. Reap only the directly owned child using short wait0/capture/queue polls within the existing cleanup deadline. Record the exact exit125 if observed; another exit is retained as a negative. Then drain, and record `after_owned_reap_observer_handles_held` while the Job and query handles remain open. Record outstanding handle identities/counts with every snapshot.
5. Independently close every observer PID handle, retaining each success/error even with an existing primary failure. Do a final bounded queue drain in **no-new-open mode** to the first current-empty result, batch/global bound or deadline. Late PID messages remain raw and get `not_queried_terminal_drain`. Record `after_observer_pid_release_before_job_close`; any failed closes are explicitly outstanding. Keep the port until this drain finishes. Never wait for particular messages or claim the queue is permanently empty.
6. Invoke the inherited owned-child/stdio/Job cleanup even if observation or close steps fail, then close the completion port independently. Preserve primary, observer and cleanup errors separately. Emit unconditional post-lease cleanup evidence, late-failure supplements, terminal seal and all marker vetoes. Missing boundary evidence or failed closes prevents complete diagnostic status.

Holding a handle can change the observed lifetime: Microsoft documents that a failed-limit association increments TotalProcesses, can temporarily increment ActiveProcesses, and the active count is released only after process termination and remaining references disappear. Therefore held and released snapshots must remain distinct; neither may be normalized. This is an observer limitation, not an explanation of any prior anomaly. [Accounting semantics](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [active-limit reference lifetime](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).

## Interpretation, tests and freeze gate

The machine contract fixes field names and negative outcomes. Journal sequence records parent observation order. API start/end intervals and dequeue times are not kernel event timestamps; accounting and PID queries are not atomic. Notifications generally are not guaranteed. PID reuse before OpenProcess can defeat historical attribution; an open handle protects the object subsequently queried, not the earlier notification's identity. No observed second PID is not proof there was none. An ACTIVE_PROCESS_LIMIT notification with NULL PID identifies no rejected child. An extra image/membership observation can support a bounded attribution only with its exact timing/creation/handle evidence and those limits.

Pure fake-API tests must cover layout/bindings/setup failure before creation; NULL quota/zero messages without PID opens; false-empty output undefinedness; false/non-NULL and wrong-key preservation; unknown/out-of-range PID; duplicate PID opens once; 64-packet/16-PID/1,024-call/batch bounds; query denial/gone/reuse uncertainty; immediate registry plus independent close failures; changed held-vs-released snapshots; cap/pre-stop/post-stop timing; raw anomaly retention without acceptance; publication failure plus guaranteed cleanup; and sealed terminal output/lease inventories. No real API or worker is permitted during preparation. Bind unchanged source/EXE/SDK/sealer, prior failed outputs and independent verification, design/contract, SDK headers, pure proof and exact new helper/protocol hashes before peer/root review. No attempt is authorized by this design.
