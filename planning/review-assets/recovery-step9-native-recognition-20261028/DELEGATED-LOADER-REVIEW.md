## Practical decision

Recommend a separately approved, finite public-C bridge that explicitly loads **one exact pinned CPU backend**, requires the returned registry and sole registry entry to match the approved CPU implementation, and then calls `llama_backend_init` once. The reviewed initializer cannot enter its automatic discovery branch when that registry remains nonempty. Failure of the explicit load or any identity/count check must terminate; there is no `load_all`, directory scan, GPU/RPC fallback, inference, or context creation.

This is a **design recommendation with two focused source prerequisites**, not current native execution authorization. `ggml/src/ggml-backend-dl.h` and the candidate `ggml/src/ggml-cpu/ggml-cpu.cpp` must resolve explicit-load and CPU-registration behavior at this exact revision. The latter implementation location has not been verified remotely. Runtime build/import provenance and module allowlists remain necessary because the registry's conditionally compiled constructor runs during registry access; a CPU name/count check alone does not prove that an unwanted constructor never ran.

## GGUF parser: what no-allocation actually skips

The no-allocation branch is now directly visible in [gguf.cpp:822](D:/Projects/drug_target_agents/data/cache/r09-native-recognition-followup-source-20261028T164431Z/sources/ggml/src/gguf.cpp:822). With `params.ctx != nullptr` and `params.no_alloc=true`, it allocates `n_tensors * ggml_tensor_overhead()` bytes for a GGML metadata context, then creates empty tensor descriptors. The binary tensor blob allocation and `gr.read(data->data, ctx->size)` occur only under `!params.no_alloc` (830–928). This resolves the previous delegated question: the reviewed parser path does not explicitly read the weight blob when no-allocation is true.

It still reads and stores the header, key/value values, strings/arrays and tensor descriptors. It computes aligned data offsets and tensor sizes. The logical alignment seek updates the reader's offset; it does not itself read padding or weights (376–385, 780–819). The file reader obtains total remaining size by seeking to end and back, and its actual callback uses `fread` for requested ranges (249–266, 948–981). `gguf_init_from_file` opens read-only, invokes the parser, and closes its `FILE*` on normal return (1017–1027).

This supports a precise claim of **no explicit tensor-blob read in the inspected no-allocation parser path**, combined with the existing vocabulary-only return before `load_tensors`. It does not support “zero OS weight I/O”: CRT buffering, filesystem read-ahead, whole-file hashing required by a future input gate, and DLL/OS internals have separate behavior. No such I/O was measured here.

The parser validates versions, counts, remaining bytes, tensor layout, and arithmetic overflow. It is not a small-memory sandbox: individual string/array limits are `1024*1024*1024`, and metadata allocations scale with retained values and tensor count (20–21, 278–357, 524–540, 790–855). Vocabulary structures and duplicated metadata add further memory. These checks do not demonstrate practical fit for the three pinned shards or a 300-second scientific case budget.

## File sizing, mappings and ownership

`llama_tensor_weight` now resolves to an index-only constructor: it looks up a descriptor, adds metadata offsets, and checks the end against `llama_file::size()` with an overflow check. It does not call a data read. See [llama-model-loader.h:32](D:/Projects/drug_target_agents/data/cache/r09-native-recognition-followup-source-20261028T164431Z/sources/src/llama-model-loader.h:32), lines 32–48.

On Windows, the named `llama_file` constructor uses `ggml_fopen`, obtains the OS handle, seeks to end to store size, and returns to the beginning (mmap.cpp 87–95). `size()` returns the stored value (420). The direct `ReadFile` loop is a separate `read_raw` operation (130–144). The named file wrapper owns and normally closes its `FILE*` (178–181, 407–409); its `FILE*` constructor marks the handle borrowed. The selected proposal uses exact named shard paths, not the `FILE*` route. See [llama-mmap.cpp:87](D:/Projects/drug_target_agents/data/cache/r09-native-recognition-followup-source-20261028T164431Z/sources/src/llama-mmap.cpp:87).

`llama_files`, `llama_mmaps` and `llama_mlocks` are vectors of `unique_ptr` (mmap.h 16–18), and the loader owns them as members. Its `metadata_ptr` and context vector use aliases declared outside this subset (loader.h 118–132). The inspected GGUF `free` deletes its context; GGML `free` releases owned aligned context memory (gguf.cpp 1030–1034; ggml.c 1674–1683). The exact custom-deleter alias definitions remain uninspected through `ggml-cpp.h`/`llama-impl.h`; therefore complete in-process RAII closure is not newly certified. This is a bounded limitation, not a reason to expand to every private compile dependency. Only public headers and bridge-owned code are intended for compilation.

`ggml_fopen` converts UTF-8 paths and uses `_wfopen` on Windows (ggml.c 618–636). Mapping creation uses the separate `llama_mmap` implementation, including Windows `CreateFileMappingA`/`MapViewOfFile` (mmap.cpp 589–608). The earlier caller review establishes that `vocab_only=true` returns before its mapping/tensor path. Continue to force `load_mode=NONE`, `lazy_mode=OFF`, no-allocation, no tensor checking, and a non-null empty device list. Do not weaken the essential vocabulary-only gate.

These normal-cleanup statements do not cover every exceptional upstream path: a constructor throwing after raw file acquisition or a C++ exception escaping the parser's normal-close path may leave resources until process exit. The reviewed code does not establish a leak-free library under all failures. A short-lived owned worker with bounded capture, measured resources, failure preservation and OS process cleanup remains the final containment boundary.

## Initialization decision and finite next work

The retained `ggml_init` first-call block self-initializes timing, then allocates a context; it does not enumerate a backend or initialize a CPU backend (ggml.c 1622–1661). The old `llama_backend_init` comment mentions F16 tables, but this exact `ggml_init` body only shows timing as first-call work. This makes a no-backend-initializer vocabulary-only bridge technically plausible for this narrow path; it does **not** turn omission into general supported public-API practice. The public header still says to call `llama_backend_init` once. The selected recommendation respects that lifecycle after an explicit CPU registration and avoids relying on a silent API deviation.

The existing source shows `ggml_backend_load(path)` using `get_reg().load_backend(path)` and initializer discovery only when count is zero. Explicit loading still calls a dynamic loader and the backend's initializer; registry construction conditionally registers compiled providers. These are the exact reasons for the two focused prerequisite references above. The next review should decide their acceptability, not broaden into a new inference backend or transitive source build.

If qualified and separately authorized, the bridge sequence should be: verify all exact modules and three shards; load only approved module paths; explicitly register the single pinned CPU provider; require approved registry identity/count; call the initializer once; obtain native default parameters and apply the conservative overrides; call the explicit ordered-splits API; assert a non-null vocabulary and expected architecture/identity; run only the bounded recognition corpus; release samplers before model, call the paired backend free, and exit the owned worker. No context, graph, decode, logits, server, fallback or model-quality claim is introduced. Backend free is not a general DLL-unload guarantee.

Actual ABI round-trip, grammar/EOG conformance, deadline/memory feasibility, module-load evidence, clinical interpretation, human review and fresh-source gates remain separate. This source review changes none of their acceptance statuses.
