## Why suspended creation is required

The current C++ program loads required OpenMP and the three core DLLs near the start of `wmain`. An ordinary running `Popen` followed by Job assignment would allow those package DLL loads to race containment. The prospective parent therefore directly invokes public `CreateProcessW` with an absolute application path, mutable UTF16 command line, `CREATE_SUSPENDED | CREATE_NO_WINDOW | EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT` (`0x08080404`). It uses no shell, Python worker, venv redirector, private `_winapi`, Nt function or guessed opaque process record. The public API returns both process and primary-thread handles/PIDs. See [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) and [creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).

Before the sole resume, the parent must configure an unnamed Job, create the exact suspended process, assign its returned handle, verify exact Job membership, read back limits, query the owned process image/creation time and thread identity, and require one assigned/active PID equal to the returned PID. It durably journals the assignment and a resume reservation. Only then may `ResumeThread` be called once; its previous suspension count must be exactly1. Failure or accounting disagreement stops before resume and terminates/reaps the owned process. The held OS-accounting diagnosis cannot be bypassed by ignoring those fields. [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) and [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread) describe the relevant public behavior.

This ordering covers the program's explicit package `LoadLibraryExW` calls. It does not assert that the OS maps no executable/CRT image or allocates no memory before assignment. Microsoft explicitly distinguishes prior allocations from later Job-limited allocations. Real execution and before-resume observations are still unperformed.

## Public layouts, inheritance and environment

The x64 types reproduce the pinned SDK fields: `SECURITY_ATTRIBUTES=24`, `STARTUPINFOW=104`, `STARTUPINFOEXW=112`, `PROCESS_INFORMATION=24`, basic/extended Job limits64/144, accounting48 and a bounded16-PID list136 bytes. `STARTUPINFOEX.StartupInfo.cb` is112. Stdio offsets are80/88/96 and the attribute-list pointer is104. Sizes/offsets are checked before any possible API construction. The public opaque attribute-list storage is sized through `InitializeProcThreadAttributeList`; its private contents are never decoded. [STARTUPINFOEXW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-startupinfoexw) documents the structure and size requirement.

Exactly three inheritable handles are listed in `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`: NUL stdin and separate stdout/stderr pipe writers. `bInheritHandles=True` is required for that list. Parent readers, Job/process/thread handles, leases and Python capture files are excluded; parent writer copies close immediately after successful creation. See [handle-list semantics](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and Microsoft's [redirected-I/O pattern](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output).

The explicit environment contains only fixed Windows System32 lookup, output-local TEMP/TMP and OpenMP thread limits1. It contains no tokens, proxy settings, Python path, backend search override or inherited user PATH. Its exact dictionary/hash is archived. UTF16 validation rejects NULs, lone surrogates, ambiguous case-insensitive environment names and oversized blocks. The only target argv is the fixed executable, `--abi`, the approved runtime mirror and an empty exclusive child output directory. No pack, CPU-backend basename or model path is supplied.

## Bounds and ownership

The proposed whole parent budget is60s, with5s for finalization. The conservative owned-child attempt budget is30s, including launch setup and cleanup;28s are usable before the reserved2s termination/reap interval. There is one attempt, no retry, no fallback and no inference. Measured child duration is separated from later parent input rechecks/sealing. A deadline failure remains a failure even if artifacts exist. Checks cannot preempt every synchronous filesystem/OS call; no absolute responsiveness guarantee is inferred from this unexecuted draft.

Job flags are `KILL_ON_JOB_CLOSE`, process commit256MiB, whole-Job commit256MiB and active-process limit1 (`0x2308`), without breakaway flags. Limits are read back before resume and observed peaks retained on successful completion. Actual accounting must remain consistent during and after the child. A configured limit is not evidence that it worked here: the harmless-worker qualification must establish this environment's behavior. These are commit limits, not working-set claims. [Extended Job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) defines the separate memory fields.

Public `PeekNamedPipe` and bounded reads drain each pipe without reader threads. Each raw stream retains at most64KiB. Overflow records a lower bound on observed bytes, marks truncation and stops the attempt; unread bytes are unknown. There is no blocking reader-thread cleanup to qualify. Process/thread/pipe/Job handles have independent cleanup attempts. On failure, the parent uses the owned Job where assigned and the exact returned process handle as fallback, waits with its remaining bound, then closes handles. Failure to reap or close remains explicit; the primary error is preserved. No foreign process is opened and no global process enumeration is needed.

## Input identity and evidence persistence

The prospective configuration retains all193 original build pins and adds reviewed build outputs, this helper and relevant SDK/reference evidence. Original executable/DLL/header paths receive read-only, no-write/no-delete-share leases. Canonical handle paths, file attributes, size and complete SHA-256 are checked before dispatch and again before sealing, while original leases remain held. No GGUF or E: path is eligible. The CPU DLL may remain pinned as an existing input but is forbidden by the ABI child's loaded-module policy. OpenMP may initialize because the pinned base DLL imports it; zero package initialization or zero OS side effects are not claimed.

The new parent output is reserved before dispatch through the accepted installed `RunJournal`. Hash-chained events retain Job configuration, the attempt reservation, returned PID/thread IDs, exact assignment checks, resume attempt and terminal failure/success. If interruption follows a resume reservation without an observed return, resumption is **unknown/may have run**; it is never reported as zero native activity. First-pass draft/check evidence was preserved before this accounting clarification.

Success still means **raw ABI observations retained, independent qualification pending**. The child must finish with its exact ABI claim and complete JSONL, no partial/failure marker or extra child files, a4MiB JSONL cap,64KiB row cap and4KiB attempt cap. Full raw module inventories, public layouts, version and every default field are retained. No expected version is guessed: a future recognition contract must bind a reviewed nonempty ABI observation. The fixed bridge calls version/defaults only; its source call policy is distinct from instrumentation or a universal claim about DLL initializers, registry reads or network/file effects.

Parent effective configuration, raw captures, attempts, journal and report are hashed into a receipt. Any authoritative failure marker—including post-receipt lease/deadline failure—overrides a receipt/status. Inputs, old failures, original build and packs are never rewritten. Abrupt parent death or unavailable storage can still prevent final sealing; an external owner must retain and disposition incomplete attempts without restarting them.
