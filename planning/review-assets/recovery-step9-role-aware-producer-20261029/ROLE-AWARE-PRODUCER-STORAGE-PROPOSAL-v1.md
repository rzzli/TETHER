# Role-aware producer and storage proposal (design only)

The next successor should hash every declared original under one owner, while retaining content bytes only for explicitly captured software or metadata. A hash-only input retains all raw calls, query frames, digest outcomes and close rights; it has no assembly/blob and stays `capture_state=not_requested`. A byte consumer cannot substitute a digest, `None`, or a fabricated empty blob for captured evidence. The accepted indexed V3/N4 profile and its existing fixtures remain unchanged.

The [normative JSON](ROLE-AWARE-PRODUCER-STORAGE-PROPOSAL-v1.json) defines versioned roles/context semantics, raw-first failure transitions, a concrete packed evidence representation, serialization ordering and the next finite source gate. It does not authorize implementation or input access.

The [historical metadata vector](RETAINED-HISTORICAL-RESOURCE-VECTOR-v1.json) preserves every one of 213 declared paths, roles, sizes and hashes without inspecting a target. All were positive and total 9,017,363,392 bytes. Its 192 software files (25,413,523 bytes) are not inherited into a new import/consumer graph. The consumed 259,867-byte old pack and 16 old owner/output records are excluded from new84 admission. The [prospective known subset](PROSPECTIVE-NEW84-KNOWN-RESOURCE-SUBSET-v1.json) instead names four native/model resource descriptors, five accepted source references, six required new84 metadata documents and the 37,766-byte logical pack. The latter has never been persisted. This subset has 712,415 captured bytes and 8,989,020,320 hash-only bytes; it is not a complete runtime roster.

The proposal selects 1 MiB prospectively: it removes most call-record cost while avoiding the extra 3 MiB single-read workspace and larger opaque work quantum of 4 MiB. It proves neither latency nor RSS. The accepted calculator remains fixed at 64 KiB; a new protocol/formula version and complete role/size/module vector are required before this choice can admit anything.

The full-profile representation proposal reserves at most 256 files, 16,384 canonical 256-byte call cells, full 8/8202/8-byte query frames, bounded UTF-8 path/module pools and 1,024-byte immutable diagnostic records. It gives 14,800,384 bytes per complete evidence ledger at the proposed maxima. Full call dictionaries and repeated per-call paths are not retained in parallel. Candidate and terminal ledgers are separate immutable artifacts so later close facts cannot mutate a previously hash-bound candidate. A compact manifest and five packets each stay within 8,192 bytes and reference complete ledger sections rather than inline 213-file arrays. The proposed artifacts, journal, new84 structured reservation and two capture streams require 40,139,776 encoded bytes at those maxima. These are payload terms, not Python heap measurements. Original exception objects, module objects, allocator and native/OS memory still require independent resource qualification.

The unchanged N4 profile is the first behavioral gate for explicit not-requested/zero-byte states, context restrictions, raw-first faults, once-only cleanup and serialization round trips. The operational path then requires a real first-clock kernel, closed source/import/consumer graph, fourteen-export binding, physical output adapter and new84 child/parent/build/pack/protocol. Existing isolated checkers must be bound to the new complete artifacts; fake handlers or a report flag cannot fill those gaps. The owner300s/295s+5s, child120s/work117s and 256 MiB ceilings remain fixed. The old negative profile and external300s timeout remain unchanged; no replay or repair is claimed.
